# Cold boot: start a VM without its memory — 2026-09-16

## Why

A VM always comes back exactly where it was: its selected checkpoint holds
the VMM state and every page of guest RAM, and a start restores them. A
template's children are the one exception: a template was never run, so a
child of it has no state to restore and boots its kernel from the root
volume. That path exists (`vmmachine` boots cold when there is no restore
state and a kernel is configured) but nothing lets an operator take an
existing VM through it. An operator wants it for the reasons one reboots any
machine: a guest that is wedged, a kernel or init change on the disk, or
simply to stop paying for memory the guest does not need to keep.

## The operation

`sproutfsctl start <vm> --cold [--to host]`, and `{"cold": true}` on the
orchestrator's `POST /vms/{id}/start`. It applies to a stopped VM only; a
running VM is stopped first, by the operator, as today.

On the host: open the VM at its selected checkpoint, then publish a
checkpoint that **discards its memory**: every page of the RAM volume is
dropped (`Volume.Discard` over the whole volume, which is what makes the
pages read as zeroes and leaves them out of the root), and the VMM state
member is dropped with it, so the new root names no state. Then start the
guest through the existing path, which boots the kernel because there is no
state to restore. The root volume is exactly what the last checkpoint
published, so the guest's filesystem sees the boot as a power cut after that
checkpoint: the journal recovers what a journal recovers, and that is
documented as the contract.

Storage follows: the pages the discarded memory held are unreferenced by
the new root and reclaimed by the usual set difference, except where a pin
protects them; the checkpoint that dropped them is small.

## What is needed

- `volume`: a publication may drop the inherited VMM state. Today a
  checkpoint with no state of its own keeps its parent's; a discard of the
  RAM volume is the one case where keeping it would be wrong, because state
  and memory describe one instant. `VM.DiscardMemory(ctx)`: discards the RAM
  volume and publishes a checkpoint with no state, as one operation, under
  the publication lock.
- `host`: `Start`/`open` gains the cold flag; `vmmachine` already boots cold
  when `RestoreState` is empty and a kernel is configured, and the host
  already configures the kernel for template children. A cold start of a VM
  the host cannot boot cold (no kernel) is refused before anything is
  discarded.
- Orchestrator, CLI, `deploy/README.md`, `docs/hosting.md`, `docs/demo.md`.
- `internal/simtest`: the world draws cold starts too; a cold-started VM's
  model memory is zero and its disk is what the last checkpoint held; the
  guest that comes back writes anew.
- The soak: of the round's restarted VMs, half start cold; the witness
  `check` for those is `--disk-only`, and the script refills memory before
  the VM is mutated again.

## Resizing at a cold boot

A cold boot is the one moment a VM's shape can change, because nothing in
memory describes it any more. `start --cold` therefore takes `--memory` and
`--disk`:

- `--memory <bytes>` sets the RAM volume's size in the discarding
  publication. Any size the host admits is allowed, up or down; the memory
  is being discarded anyway. From then on the VM's committed RAM is its own,
  not its template's: the table records memory bytes per VM (set at create
  and fork from the template, changed here), and placement admits against
  that. This replaces the template lookup the pre-mortem added for children.
- `--disk <bytes>` grows the root volume in the same publication; the new
  pages read as zeroes, which is what a filesystem grown in place expects,
  and the guest grows its filesystem over them after the boot. Shrinking is
  refused: the filesystem's end is not the volume's to cut.

Both are refused for a warm start. The soak gives a seeded share of its cold
starts a larger memory and a larger disk, runs `sproutfs-guest-witness grow /`
in the guest, and checks the witness's disk file afterwards. The grow is the
witness's own because resize2fs cannot do it: its online path opens the block
device read-write, and a 6.18 kernel refuses a write open of a device something
has mounted, so on a guest whose root filesystem is on that device it fails with
EBUSY before it begins. `EXT4_IOC_RESIZE_FS` on a descriptor of the mount point
needs no such open.

## Proof

Red first: a host test that a cold start of a stopped VM boots with no
restore state and a RAM volume reading zeroes while the root volume holds
the last checkpoint's bytes; a volume test that `DiscardMemory` publishes a
root with no RAM pages and no state and that reclamation frees the memory's
parts; an orchestrator test over its fakes; the simtest operation; the
witness's `--disk-only`; the shell harness covering the soak's cold half.
Then `just check`, `-race` on the packages touched, 200 seeds of the topology
campaign, `TestScheduledWorldReproduces`, and the Lima Firecracker suite,
which has the real cold boot.
