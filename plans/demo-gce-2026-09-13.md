# Demo on one GCE VM — 2026-09-13

A demo, not a deployment. One disposable GCE VM runs a single-node Kubernetes
cluster; two host pods on it run VMs; a demo orchestrator drives boot, fork,
migration between the pods, and recovery after a pod is killed. Object storage
is GCS through a new backend.

Owner's answers: single GCE VM with a small Kubernetes, GCS backend, all four
flows, an invented demo orchestrator. The rest below is determined from them.

## Environment

- One GCE VM as `scripts/bench-memory-gce.sh` creates it: `n2-standard-8`,
  nested virtualization, Ubuntu 26.04, 100 GB disk, temporary labels, the
  24 h inactivity lease. A 2 MiB HugeTLB pool of 8 GiB set by sysctl at boot.
- k3s, single node, containerd. Chosen over minikube because it runs on the
  VM's own kernel with no driver layer between pods and `/dev/kvm`,
  hugepages and userfaultfd. Pods run privileged with `hugepages-2Mi`
  requests and a `hostPath` for `/dev/kvm`.
- x86_64 throughout: GCE nested virtualization is x86 only. The Firecracker
  branch builds for x86_64 with its x86_64 seccomp policy; the kernel is the
  pinned Firecracker CI `vmlinux` for x86_64; the guest is an Alpine x86_64
  ext4 image with a static init that runs a shell on the serial console.
- The GCE VM's service account has object admin on one bucket created for the
  demo; pods use the VM's metadata credentials. No keys.

## Components to build

1. **GCS object store** (`internal/platform/internal/real/gcs.go`): implements
   `platform.ObjectStore` with `cloud.google.com/go/storage` (Apache-2.0).
   `IfNoneMatch` → `DoesNotExist`; `IfMatch` → `GenerationMatch`, with the
   object generation as the `ETag`. Tested against the emulator
   (`fake-gcs-server`, Apache-2.0) in the repo's test suite and against a real
   bucket by the demo.
2. **`cmd/sproutfs-host`**: the host binary. Starts `replica.Host` with the
   GCS store, the resource budget, the pager (HugeTLB arena, spill file) and
   a Firecracker supervisor over `vmmachine`. Serves an HTTP API on the pod IP:
   create, open, fork, capture, list, console read/write, migrate-out
   (returns the handoff), migrate-in (takes a handoff), release, status.
   Interval cuts run for every VM it runs. preStop drains.
3. **`cmd/sproutfs-orchestrator`**: stateless. Discovers host pods through the
   Kubernetes API by label and VMs by listing control records in the bucket.
   Allocates VM identities (ULIDs), places new VMs on the least-loaded host,
   carries handoffs between hosts, and reopens a VM elsewhere when its host is
   gone. HTTP API plus a `sproutfsctl` CLI: `create`, `fork`, `list`,
   `console`, `migrate`, `kill-host`, `recover`.
4. **Images and manifests** (`deploy/`): one container image with the host,
   the orchestrator, Firecracker, the seccomp policy and the kernel; the guest
   image built by a script and copied to the VM. Manifests: namespace, host
   Deployment with two replicas (anti-affinity is meaningless on one node, so
   two pods it is), orchestrator Deployment, Services, RBAC for pod listing.
5. **Scripts** (`scripts/demo-gce.sh`): `create` (VM, k3s, hugepages, bucket,
   image push through the VM's containerd import), `run` (the four flows,
   printing pause and timings), `delete`. Nothing persists beyond the VM and
   the bucket; `delete` removes both.

## The four flows

1. `sproutfsctl create --template alpine` boots a VM; `sproutfsctl console`
   attaches; a command runs in the guest.
2. `sproutfsctl fork <vm> --count 20` forks a running VM; the demo prints
   per-fork start latency and the host's shared-frame count.
3. `sproutfsctl migrate <vm> --to <host>` moves it between the two pods; the
   demo prints the pause and the post-copy stream time; the console session
   survives.
4. `sproutfsctl kill-host <host>` deletes a pod; `sproutfsctl recover <vm>`
   opens the VM on the other host from its last cut; the guest resumes a few
   seconds back.

## Order and ownership

Independent of the running refactor, in worktrees: GCS backend; GCE/k3s
provisioning script and manifests; x86_64 guest image and Firecracker/kernel
build for x86_64. After stage 1b lands: the host binary, the orchestrator and
the container image, since they consume APIs that stage is changing. Then the
end-to-end run on GCE.

## Stage 2: using the VMs (added 2026-09-13)

Owner's requirement: the orchestrator can execute a command in a VM; it knows
which host every VM is on and is told when a drain starts and completes.
Scoped down twice from the original: no guest network, and no HTTP proxy into
a guest. Running a command is the whole of what a VM is used for here.

- **Guest channel.** No guest network: every VM gets a virtio-vsock device
  instead, configured on every boot and every resume with the same guest CID
  and a Unix socket in the VM's own scratch directory. A restore carries the
  device in its VMM state and the host only moves the socket, so a fork and a
  migrated VM are reachable at their new host's path with nothing carried
  between hosts and nothing to allocate.
- **Guest agent.** `cmd/sproutfs-guest-agent`, a static Go binary the guest
  image runs from init. Serves HTTP on vsock port 80 inside the guest:
  `POST /exec` `{cmd, timeout}` runs a shell command and returns exit status,
  stdout and stderr; `GET /healthz`.
- **Host.** `POST /vms/{id}/exec` reaches the guest over its vsock: connect to
  the VM's Unix socket, ask Firecracker for guest port 80, and speak HTTP over
  what comes back.
- **Orchestrator table.** SQLite (`modernc.org/sqlite`, BSD-3, pure Go) on a
  hostPath volume: VMs with host and state (creating, running, migrating
  from→to, stopped, recovering); hosts. Every create, fork, migrate, recover and
  delete updates it; a host's drain reports start and completion per VM.
  Discovery by survey remains the way the table is rebuilt at start.
- **Orchestrator API.** `POST /vms/{id}/exec`, routed by the table to the VM's
  host; `sproutfsctl exec <vm> -- cmd`.
- **Demo flow 5.** Exec a command in a VM, fork it, exec in the fork, migrate
  it, exec again through the orchestrator.

### Status

Built and landed: the vsock device on every boot and resume, the guest agent in
the guest image, the host's `/vms/{id}/exec`, the orchestrator's SQLite table
with drain reporting and exec routing, `sproutfsctl exec`, and flow 5 in
`scripts/lib/demo-run.sh`. `docs/demo.md` and `deploy/README.md` describe them.

## Not in scope

TLS, membership, authentication, multiple nodes, durability measurements,
reclamation beyond what the cut model already does.
