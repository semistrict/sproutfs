# A GCE soak: forks, migrations, stop and start under a workload — 2026-09-16

## Why

The demo flows prove each operation once. Nothing on a real cluster yet
takes many forks across the same host and other hosts, migrates and stops
and starts them with a workload running in between, and checks after every
step that every guest's memory and disk hold exactly the bytes that guest
wrote. The simulated campaigns do that with model guests; this is the same
discipline over Firecracker, KVM, the pager, GCS and k3s.

## Two new operations

`stop` and `start` do not exist yet and the soak needs them.

- `sproutfsctl stop <vm>`: the orchestrator asks the host running the VM to
  take a final checkpoint, close the VM and release its pages; the table
  records it `stopped`. Refused while a fork point holds the VM sealed, as
  a delete is. Host endpoint `POST /vms/{id}/stop`, orchestrator endpoint
  `POST /vms/{id}/stop`.
- `sproutfsctl start <vm> [--to host]`: the orchestrator places a stopped VM
  on a ready host by committed RAM, or on the named one, and opens it there
  at its selected checkpoint through the host's existing `open`. Refused
  while a host runs it. This is `recover` without the loss evidence, because
  the table says stopped and the last host closed it; `recover` stays for
  the lost case. Orchestrator endpoint `POST /vms/{id}/start`.

Both get unit tests over the orchestrator's fakes, a host test, a `World`
operation in `internal/simtest` so the seeded campaign draws them, and rows
in `deploy/README.md`'s API tables and `docs/hosting.md`.

## A deployment check from the CLI

`sproutfsctl check` runs `volume.CheckDeployment` over the bucket, through a
new orchestrator endpoint `GET /check`, with the allowances a live deployment
needs (in-flight publications, the pinned checkpoints of deleted VMs, the
templates), and reports every violation. The soak runs it at the end with
every VM deleted, when nothing but the templates and pinned checkpoints may
remain.

*The templates that leaves are one per guest image, named by the image's bytes
rather than one per host pod per import — see
[a template named by its image](template-by-digest-2026-09-16.md).*

## The witness

A guest needs to say whether its memory and disk are what it wrote. A small
static Go binary, `sproutfs-guest-witness`, is built like the guest agent and
put in both guest images by `scripts/build-guest-image.sh`:

- `witness fill --memory 256M --disk /var/witness --seed S`: maps a buffer
  of that size, fills it and a file of the same size with a deterministic
  pattern of (seed, step 0), and stays resident, serving a unix socket.
- `witness mutate --step K`: through the socket, rewrites a seeded fraction
  of the buffer and the file with the pattern of (seed, K), touching pages
  across the whole range so dirty sets are scattered.
- `witness check --seed S --step K`: through the socket, verifies every
  byte of the buffer and re-reads and verifies the file against the pattern
  of (seed, K); exits non-zero naming the first mismatching offset. The
  pattern is a pure function, so the expectation lives in the script, not in
  the guest.

A fork's children inherit the parent's (seed, step) and are checked against
it before anything else; then each child mutates under a seed of its own.
The witness's pattern and mismatch detection have unit tests.

## The soak

`scripts/lib/demo-soak.sh`, run as `scripts/demo-gce.sh soak`, over the
two-host demo cluster. Parameters, with defaults that fit two 512 MiB-guest
hosts: rounds (6), forks per round on the parent's host (2), forks per round
to the other host (2), VMs migrated per round (2), VMs stopped and restarted
per round (2), memory and disk witness size (256 MiB each).

Each round, over every running VM in a seeded order:

1. Mutate memory and disk, then check.
2. Fork the fan-outs, on the parent's host and to the other host; check every
   child against the parent's state, then the parent; then mutate each child
   under its own seed and check again.
3. Migrate the round's share; check each before and after.
4. Stop the round's share; check they are absent from every host; start them,
   some on the other host; check each.
5. Delete a seeded share so the population stays within what the hosts
   admit; a placement refused with 503 is recorded, not failed.

Once per soak, at a seeded round: kill one host pod without grace, as the
fixes flow does, recover its VMs on the other host, and check each against
its last checkpointed state — the witness's step at the last `capture`, so
the script captures before mutating in that round.

At the end: delete every VM, run `sproutfsctl check`, and print the round
table: operations, timings (fork pause, migration pause and stream, stop,
start), object-store operations per host from `/metrics`, and every check.
Everything is recorded under `.workload-runs/soak-<timestamp>` as the
workload flow records its runs. Non-zero exit on any check failure.

## Proof

- Unit tests for stop, start and check at the host, the orchestrator and the
  simulated world; the witness's tests; `shellcheck` on the scripts;
  `just check`.
- The GCE run itself is the owner's, not an agent's: `create`, `soak`, then
  `delete` with its verification.
