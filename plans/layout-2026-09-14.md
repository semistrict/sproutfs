# Repository layout — 2026-09-14

Decision by the owner: nothing in this module is a library. No other module
imports it, and none is meant to. Today most of it sits at the repository root,
where Go's rules make every exported name in every package part of a public
surface the project does not have and does not want. The target makes that
explicit: every package but the commands is private, the large packages carry
their bodies in nested `internal` directories, and the few boundaries that
matter are boundaries the compiler enforces rather than ones a reviewer
remembers.

## Target shape

```
cmd/sproutfs-host, cmd/sproutfs-orchestrator, cmd/sproutfsctl, cmd/sproutfs-guest-agent
platform            ports: object store, disk, network, metrics
platform/internal/{real,gen}   the real adapters and the generated protos, nameable from nowhere else
platform/adapters   the constructors that build them, each returning a port
platform/sim        the simulated adapters, which every package's tests drive the real code over
internal/{resource,control,ctxsync,jsonhttp,blob}
checkpoint          (was image) with internal/{pack}
volume
vmmemory            with internal/{pageranges,latency,slots}
internal/vmwire              the Linux syscalls vmmemory's sessions are made of
vmmigrate           with internal/{wire,peer}
vmmachine
host                the host's own work + its capture operations + the supervisor's lifecycle, one Machine interface
internal/api/{host,orch,guest}   wire types only, no runtime imports
internal/{testbacking,testnet,testrepro,testresource}   fixtures no non-test package imports
internal/vmtest              the Rust memory client qualified against a real Go pager
```

`internal/vmwire` is the one exception to the nested-internal rule. Its
sockets, memfds and userfaultfd calls are `vmmemory`'s implementation and would
belong under `vmmemory/internal`, but `vmmachine` and
`internal/vmtest` build the same fixtures in their Linux tests, so it is a
package of its own.

The five test-support packages are not fixtures a package hides in its own
`_test.go` files because more than one package needs each of them:
`testresource` is the roomy host allotment every test that is not about
capacity takes, `testbacking` the volume wrapper that makes a simulated run
order two pagers' memory regions the same way twice, `testnet` the real loopback
transport, `testrepro` the cross-process replay checker, and `vmtest` the Go
pager the Rust client is qualified against. Nothing outside a test file imports
any of them, which `go list` can say and this plan does not have to.

Two details differ from the sketch this started as, both forced. The
constructors are `platform/adapters` rather than `platform` itself: an
adapter imports `platform` for the ports it implements, so `platform` cannot
import an adapter back. And `sim` stays beside `platform` rather than under its
`internal`, because the simulated adapters are not an alternative a process
chooses at startup — they are what the whole module's tests drive the real
`control`, `checkpoint`, `volume`, `vmmigrate` and `host` implementations
over, and no package outside `platform/` could reach them from under
that `internal`.

## Why

**Everything is private by default.** Nothing in the module is a library, so
`internal/` is the right default and the root is reserved for `cmd`, the module
files and the supporting directories (`docs`, `plans`, `scripts`, `deploy`,
`rust`, `third_party`). A package that has to be reachable from outside
`internal/` is then a deliberate exception, and there are none.

**Nested internal packages carry the private bodies of the large packages.**
`vmmemory`, `vmmigrate` and `checkpoint` are each big enough that their internal
seams want to be packages, not files — but those seams are implementation, not
interface. `vmmemory/internal/arena` is importable only from
`vmmemory`, so splitting a package does not widen it.

**The pager must not depend on the checkpoint store.** `vmmemory` names pages by
page identity — the (checkpoint reference, volume, page) triple — and serves
them from wherever it has them: a resident page, a peer's page server, or a
store read behind an interface it does not own. That identity is a control-record
notion, not a store notion: the reference is a (VM, sequence) pair the control
record allocates and selects, and the identity is what makes two memory regions share a
page. Putting `Ref`, `Identity` and `Extent` in `control` lets the pager and the
migration wire name pages without linking the store that happens to hold them.

**API packages must not link the runtime.** `internal/api/{host,orch,guest}` are
the request and response types the three processes exchange. They are imported by
both sides of every hop and by the CLI; if they can reach the runtime, a client
links a pager. Keeping them to wire types and nothing else is what makes the
orchestrator's dependency on a host an HTTP dependency rather than a Go one.

**Nothing names a platform adapter.** `platform` is ports: object store, disk,
network, metrics. The real adapters are an implementation of those
ports, and which implementation a process gets is a startup decision. Moving
them under `platform/internal/real` makes that a compiler rule: no
package outside `platform/` can name `*real.Disk` or `*real.Network`
at all, so none can come to depend on an adapter's own surface. A process that
needs one calls a constructor in `platform/adapters`, and every one of
those returns a port. Generated protobuf code sits beside `real` for the same
reason — it is an adapter's encoding, not a port.

**`image` is called `checkpoint`.** The package stores checkpoints. It has never
held a guest image, and the name collides with the one this project does use
("guest image", the rootfs `scripts/build-guest-image.sh` bakes). The proto
package follows: `sproutfs.image.v1` becomes `sproutfs.checkpoint.v1`.

## Steps

Step 1 (this change) is mechanical and changes no behaviour.

1. **Page identity moves to `control`.** `Ref` (VM, sequence), `Identity`,
   `ZeroIdentity` and `Extent` leave the checkpoint store for `control`, which is
   where the notion belongs. `vmmemory` and `vmmigrate` stop importing the store.
2. **`image` becomes `checkpoint`.** Directory, package name, import path, proto
   package, generated code, buf configuration, mutation-testing paths, docs and
   plans. "Guest image" wording and the guest-image scripts keep their names.
3. **Everything but `cmd` moves under `internal/`.** `platform` keeps its ports
   at `platform`, with the real adapters and the generated code below
   its own `internal`, the constructors in `adapters` and `ctxsync` promoted to
   `internal/ctxsync`; `internal/{hostapi,orchapi,guestapi}` become
   `internal/api/{host,orch,guest}`.

A package named for a thing the code also has a variable for shadows it. Two
of the new names do: local variables called `checkpoint` become `ckpt` — the
abbreviation the object layout already uses in `vm/<id>/ckpt/<seq>/` — in the
files that import the store, and in the two commands the package-level type
`host` becomes `service` (the host binary's own API surface) and `liveHost`
(the orchestrator's surveyed host), with their locals renamed alongside.
Methods and struct fields keep the word; neither shadows anything.

Later steps, not in that change:

- Split the large packages into their nested `internal` bodies:
  `vmmigrate/internal/{wire,peer}` (which is where `platform/wire` ends up),
  `checkpoint/internal/pack`. Done for `checkpoint/internal/pack`: the part
  layout — the member writer, the table and the trailer — is a package, and the
  store, index, publication, cache, reclamation and compaction that use it are
  not. Done for `vmmigrate/internal/wire`: the frame codec and its proto moved
  there from `platform/wire`, because migration is the only thing that frames
  anything, and its generated code joined `vmmigrate/internal/gen`. Done for
  `vmmigrate/internal/peer`: the destination's connection pool and its two
  requests are a package that holds no policy, and `PeerBacking` — which pages
  only the source has, when to wait out a busy source, when to stop asking —
  is what remains.
  The pager is done: its nested bodies are
  `vmmemory/internal/{pageranges,latency,slots}`, not the sketch's
  `{arena,spill,uffd,bindings}`. The arena's slots, the spill file, the UFFD
  session and the binding blocks all read and write the pager's own state under
  its metadata lock, so a package boundary at any of them would export that
  lock; the three that moved reach nothing of the pager at all. The rest of the
  package is now files by concern rather than one 2,365-line file.
- **Done.** Consolidate `replica`, `vmcapture` and the host supervisor's
  lifecycle into `host` behind one `Machine` interface.
- **Done.** Decouple the API packages: they must import nothing from the
  runtime.

## Status

Step 1 landed, then the package splits, then the host consolidation and the
API decoupling, in three changes.

**`host` is one package.** `internal/replica` and `internal/vmcapture`
are gone and the VM-lifecycle half of `cmd/sproutfs-host`'s supervisor is here
with them. `Host` is what the deployment runs on this machine — the object
namespace, the page cache, the volume manager, the page server and the loops
that keep what it runs durable and fenced — and `Capture`, `Seal` and
`CreateFork` are its capture operations rather than a package of their own.
The supervisor behind it — `host.Start`, which returns the `host.Service` the
command serves — owns the pager over its arena and spill file, the Firecracker
processes, the templates guest images are imported into, and the channel to the
agent in a guest. `cmd/sproutfs-host` keeps its configuration, its HTTP handlers
and the wiring. One `Machine` interface replaces `vmcapture.Runtime`,
`replica.Machine` and `replica`'s use of `vmmigrate.Runtime`; `vmmigrate` keeps
the smaller `Runtime` a handoff needs, which a `Machine` satisfies.

**Only the commands choose an adapter.** `host` and
`vmmachine` are given `platform.ObjectStore`, `platform.Network` and
`platform.Disk` in their configurations, and `cmd/sproutfs-host` and
`cmd/sproutfs-orchestrator` are the only non-test packages that name
`platform/adapters` (`internal/testnet` is test-only and may), which
`cmd/sproutfs-host`'s TestOnlyTheCommandsChooseAnAdapter states as the importer
set `go list` must report, on both operating systems. A VMM's
staging directory is the one place a directory could not become a port — the
sockets and the binary beside it need real paths — so `platform.Disks` is the
port for it: open a `Disk` rooted at a directory the package made.

**A proto sits beside the package that owns its generated code.** Every other
`.proto` is under its package's own `proto/` with the generated Go under that
package's `internal/gen`. The simulator's trace was the exception: its source
was under `platform/sim/proto` while `buf` put the Go under
`platform/internal/gen`, where `platform`, `sim` and the adapters can
all name it. The source moved to `platform/proto` to match; the
generated bytes are unchanged.

**The API packages carry wire types only.** `api/host` declares the
handoff and the object-store tally itself instead of aliasing
`vmmigrate.Handoff` and `platform.ObjectTraffic`, and the host converts at its
own boundary. `go list -deps ./cmd/sproutfsctl` now names
`internal/api/{guest,host,orch}` and `internal/jsonhttp` and nothing else; the
JSON is unchanged, so a running control plane reads the same bytes.
