# The Firecracker qualification on x86_64 — 2026-09-26

This is TASK-11: the Linux qualification of `scripts/bench-memory-gce.sh` with
`SPROUTFS_GCE_QUALIFY=1`, on a disposable GCE host. It ran once per arena mode,
`SPROUTFS_ARENA=shared` and `SPROUTFS_ARENA=isolated`. The raw logs are under
`docs/measurements/gce-qualify-20260926-*` on the machine that ran it. They are
not versioned.

## The host

- `n2-standard-8` in `us-east4-a`, Intel Cascade Lake at 2.8 GHz, nested KVM.
- Ubuntu 26.04, kernel `7.0.0-1011-gcp`, x86_64.
- A 2 MiB HugeTLB pool of 4096 pages.
- Go 1.26.6, Rust 1.97.0. Firecracker is the `sproutfs` branch at `12be3bbbd`,
  built debug for `x86_64-unknown-linux-musl` with `sproutfs-memory`.

## What the first run found and this run fixed

The first shared run failed three Firecracker tests. Two were the fixture's,
and are fixed in `eee20f34`:

- `TestAStarterPlacesTheVMMAndItsDevices`. The jailed VMM failed with "Managed
  memory: Permission denied". Ubuntu 26.04 mounts `/tmp` with `nodev`, and the
  jail's `/dev/kvm` and `/dev/userfaultfd` are nodes made in a test directory
  there. The qualification host now remounts `/tmp` with devices. A directory
  elsewhere would make the suite's Unix socket paths too long.
- `TestPulledGuestsFaultWithoutTheObjectStore` could not write its fill. The
  64 MiB root has 39 MiB free on x86_64, and the test wrote 40 MiB. It writes
  32 MiB now, which is still four pages more than the arena.

Before that run the root also lacked `dd` and `sync`, which the pull test uses.
`80d79f35` adds them, as the Lima root already had.

## What still fails

**`TestAGuestTouchingAllItsRAMLeavesItsNeighbourItsWorkingSet`**, in both
modes. The hostile guest's RAM hog never finishes its first pass. The test waits
two minutes for "SPROUTFS_HOG_PASS kind=ram" and times out. The hog stores into
80 MiB of its 128 MiB RAM, and the arena is 96 MiB for both guests. When the
hostile guest had booted, the RAM pager had already made 328 evictions, 328
spills and 312 refaults. The host logged no error, and the guest's console
shows the hog start and nothing more. It passes in Lima on aarch64. It needs a
reproduction on x86_64 before anything is changed.

**`TestPulledGuestsFaultWithoutTheObjectStore`**, in both modes. The parent's
pull and its reads pass. The child's pull does not share the parent's copy of
the fill:

```
the child's pull of 53781652 bytes took 52502528 more of the disk, want the
32 MiB fill shared with the parent
```

The child's pull copied almost every byte again. The test wants at most the
child's bytes less the 32 MiB fill. It passes in Lima on aarch64.

Both failing tests logged `arena:shared` in the isolated run. So at least these
two build their pagers without reading `SPROUTFS_ARENA`, and the isolated run
did not change them.
