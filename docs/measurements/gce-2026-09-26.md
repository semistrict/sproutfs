# The GCE run of the merged code — 2026-09-26

One demo cluster on GCE ran every cluster check after the features merged
since [the soak of 2026-09-17](../measurements-2026-09-17-soak.md). The cluster
is `scripts/demo-gce.sh create`: one `n2-standard-8` in `us-east4-a`, k3s, two
host pods and GCS. It started at `3e3615e0` and was redeployed with each fix
below. The VM, its disk and its bucket were deleted at the end, and `delete`
verified that they were gone.

The arena modes are in [their own write-up](arena-modes-2026-09-26.md), and the
x86_64 Firecracker qualification in [its own](firecracker-x86_64-2026-09-26.md).

## The merged features

`scripts/demo-gce.sh features` runs `scripts/lib/demo-features.sh`. Each of
these was done once through `sproutfsctl` or a host's API, and its result was
checked, in both arena modes:

- `capture --keep` kept a checkpoint with the guest's memory. `kept` listed it.
  `create --from VM@CHECKPOINT` resumed a new VM at it after the VM had moved
  on. A release of that checkpoint was refused, because a VM came from it. A
  release of another kept checkpoint gave it up.
- `stop --suspend --keep` kept the stop's checkpoint. `create --from VM` and
  `create --from VM@CHECKPOINT` both resumed where the stop paused the guest,
  and `start` resumed the VM itself.
- `capture --new` made a stopped VM, and `start` resumed it where the capture
  paused the first.
- `create --ephemeral 256M` gave the guest `/dev/pmem1`. A migration carried
  its bytes, and a fork's child found it zeroed.
- `create --pull` copied the VM's whole memory onto its host's disk, and the
  host reported the pull done with every byte.
- `import-template` took an image no host was configured with. The template was
  named by the image's sha256, a VM booted from it with the image's marker, and
  a second import named the same template.
- A host imported a template for tenant `acme` and created `acme/…` from it.
  `GET /stored?tenant=acme` billed that VM, and `GET /stored` did not list it.
  Tenant `beta` was refused both acme's template and acme's VM, with 400. After
  the delete, acme was billed nothing for the VM.
- A failed receive was retried: see TASK-17 below.

## TASK-17: a host lost during a real migration

`fixes` now has `lost-migration`. A 3 GiB guest writes 2.5 GiB into a tmpfs
that no checkpoint holds, so the post-copy lasts long enough to lose a host in
it. The run waits until the destination has started the guest, then kills a
pod with `sproutfsctl kill-host`, which is `POST /hosts/{name}/kill`.

- **The destination killed mid-stream.** The receive failed, the orchestrator
  tried the handoff again on the pod that replaced it, and the VM landed there
  with every byte it had written, by md5. The migration's pause was 32.8 s,
  because the guest stays stopped while the receive is retried. The stream was
  22.6 s.
- **The source killed mid-stream.** The orchestrator saw the source was no
  longer listed and ended the receive. The destination discarded the
  half-received guest. A bystander VM on the lost source was reopened by an
  ordinary recovery. Both VMs ended running, and the migrating one came back
  with the marker it wrote on its root before its last capture.

Every VM ended running or reopenable, twice. One thing did not work as
designed. The orchestrator's own recovery after the lost source failed:

```
recovering vm-… after losing the host holding its pages: no host is available:
no host has 3221225472 bytes of memory free
```

The only other host was the destination. It had just discarded the 3 GiB guest,
and the survey still counted that guest's memory. The VM was left stopped, and
`sproutfsctl recover` reopened it three seconds later. It happened in both
runs.

In the first run the recovered guest booted cold. Its last checkpoint was an
interval checkpoint, which holds the disks alone, and the check read a marker
in memory, so it failed. That was the check's mistake. The marker is on the
root now, and the second run passed.

## TASK-36: the fan-out rollback and the termination budget

**A same-host fan-out that fails part way.** `fixes` now has `fanout-rollback`.
A parent with a 16 GiB root forks three children on its own host. The
orchestrator admits the fan-out on RAM, three 512 MiB guests. The host's PMEM
logical cap, 40 GiB of roots, takes the parent's and one child's and refuses
the second child at its receive. The one child already started was deleted.
The other two holds were given up, the host served no hold afterwards, and the
parent checkpointed again. It held in both arena modes.

**The termination budget.** The redeploy onto the isolated arena ran with a VM
whose memory held a marker written after its last checkpoint. Kubelet stopped
the first host pod at 19:03:54. Its drain moved nothing, and the pod was gone
within six seconds. It stopped the second at 19:04:32. Its drain moved the VM
in 1.04 s, and the pod was gone within two seconds. Neither hook failed. The VM
still held its marker on the new pod. So the drain and the shutdown behind it
fit well inside the 1920 s grace period. A drain that uses its whole 30 minutes
was not produced.

**One template per guest image.** At the end the bucket held seven templates:
four builds of the alpine image, one per redeploy, the two images the feature
checks imported, and the workload image. That is one per distinct image. About
fifteen host pods came and went, and none imported an image a second time.

## TASK-34: ten workload guests on one boot disk

`FORKS_BASE=4 FORKS_PER_REPO=2 scripts/demo-gce.sh workload` no longer reaches
the disk. The orchestrator refuses the first fork:

```
fork: no host is available: sproutfs-host-… has 1879048192 bytes of memory
free, and this VM needs 8589934592
```

The default setting, two and one, is refused the same way. A fork now admits
each child as a guest of its own RAM. A workload guest is 2 GiB, and a host's
RAM arena is 3.75 GiB, so a host holds one of them. The workload run cannot
fork on this cluster until the sizing or the admission changes.

## What was fixed on the way

Each fix is its own commit with a test:

- `65dc79a6`: every create of a template after the first on a host failed with
  "the fork point has been retired". The first VM's root gave up the last hold
  on the host's one template point. A point over a published checkpoint seals
  nothing, so its last hold going is now no retirement.
- `240612bd`: each of those refused creates left a control record, listed as a
  stopped VM at checkpoint 0. A refused hold now deletes the record.
- `4f1ea4a9`: saved memory wrapped round to about 16 EiB once a host held pages
  nothing mapped. The saving now counts only aliases past a page's first.
- `824be482`: a redeploy rotated the token and so rewound the second host's VMs.
  An apply now keeps the token the cluster holds.
- `a4c756c5`: the demo's console lines never reached the guest, so `run`
  failed at its first flow.
- `22106bf6`: `bigguest` asked for more RAM than a host's RAM arena, and forked
  onto a host with no room.
- `d60d26d1`: the fixes script read a VM's checkpoint from the wrong column.
