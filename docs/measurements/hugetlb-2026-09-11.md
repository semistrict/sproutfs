# Explicit 2 MiB HugeTLB qualification — 2026-09-11

The production pager now uses explicit 2 MiB HugeTLB resident pages for RAM
and PMEM. Allocation, lineage sharing, copy-on-write, protection, spill and
reclamation use the same unit. A page's identity includes both underlying
1 MiB storage chunks, without changing the storage format. The supervisor
requests `huge_pages: "2M"`; protocol version 4 rejects mismatched clients and
non-HugeTLB arenas. [Design and deployment requirements](../vm-memory.md).

The same 1 GiB probe used in the [earlier investigation](memory-probe-2026-09-11.md)
ran on a disposable GCP `n2-standard-8`, Intel Cascade Lake, Ubuntu 26.04 host
with nested KVM, Linux 7.0.0-1011-gcp and the pinned guest kernel 6.18.44.
The host reserved 4,096 HugeTLB pages (8 GiB). These are three-run medians;
all 21 probe results returned checksum 35,651,584.

| --- | ---: | ---: | ---: | ---: |
| Managed HugeTLB, 1 vCPU | 0.640 | 100.6 | 87.7 | 26.0 |
| Managed HugeTLB, 4 vCPUs | 0.648 | 96.4 | 87.1 | 27.9 |
| Plain small pages, 1 vCPU | 5.418 | 95.5 | 88.9 | 40.5 |
| Plain small pages, 4 vCPUs | 5.432 | 94.0 | 87.2 | 42.1 |
| Isolated plain small pages | 5.419 | 97.8 | 90.1 | 43.8 |
| Isolated transparent huge pages | 0.523 | 97.4 | 88.9 | 27.4 |
| Direct host process | 0.425 | 90.0 | 85.8 | 26.8 |

Managed first touch fell from the earlier 6.767 s median to 0.640 s, about
10.6× faster. These runs used different instances of the same host type;
the simultaneous plain controls remain near the earlier 5.36 s result.
Warm rewrites remain around 0.1 s. The six managed probes took 508–514 faults,
with 190–249 ms aggregate pager fault time, and no protection, sealing,
eviction or spill during the probe. This qualifies the x86_64 implementation;
the new aarch64 path was cross-compiled but not executed. It does not repeat
the earlier Apple nested-hypervisor experiment.

The real UFFD and KVM suites cover physical sharing, whole-page COW, sparse
zeros, fencing, capture/restore, nested forks, migration, pool exhaustion and
release. Firecracker's mapped arena ranges report a 2,048 KiB kernel page size.
The full guest pressure run used 48 pages (96 MiB), observed 50 evictions,
25 spills and 20 spill refaults, and released all arena allocation on shutdown.
A second snapshot restore mapped 64 inherited pages in two commands without
backing loads or subsequent guest faults. The 32 MiB historical fixture budget
is below the new working set; 64 MiB also thrashes when both forked guests run.
The qualification now requires spill/refault at 96 MiB.

Signal stress exposed `fallocate(..., FALLOC_FL_KEEP_SIZE, ..., 2097152)`
returning `EINTR`. The regression failed in 0.36 s before the fix. Allocation
and punching now retry interruptions while respecting cancellation; the
signal regression and exhausted-pool recovery both pass. Allocation errors
are returned before accessing an unallocated mmap, avoiding SIGBUS.

Operational constraints remain explicit: hosts must provision a HugeTLB pool;
there is no small-page fallback. A one-byte mutation can copy and charge 2 MiB.
Mixed lineage within either storage chunk loads privately. Sparse zeros and
untouched traps own no resident page and retain anonymous kernel-zero/trap
mappings. Version 3 clients and managed captures with the former `None` page
configuration are not accepted by the new path.
