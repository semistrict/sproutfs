# The index layout against a log layout — 2026-09-28

**Status: simulated.** Both layouts ran the same page workloads on the
simulated object store. The times are the store's latency model, not a real
store's. TASK-66 tracks the work.

## The question

Hajkazemi et al., [Beating the I/O Bottleneck: A Case for Log-Structured
Virtual Disks](https://doi.org/10.1145/3492321.3524271) (EuroSys '22), store a
virtual disk as a numbered log of objects. Each object's header names the
blocks in it. No object holds a block map. A client rebuilds the map in memory
by replaying headers from the last map checkpoint. Would this format serve
Sproutfs better than its own?

Half of that design does not apply. LSVD logs every block write to a local SSD
and streams batches to the store, so it loses only a prefix of recent writes.
Sproutfs disks are PMEM mapped through the pager. Guest stores never reach a
write call, so there is no write stream to log. What remains is the object
format, and that is what this compares.

## The two layouts

Both layouts write the same parts, with the same members, codec, compaction and
read path. They differ only in where the page table lives.

- **Index layout** (current). Each checkpoint writes an index object. It holds
  every segment of page table the checkpoint changed, and the root. Its
  create-if-absent PUT is the commit. An open reads the root. A read fetches a
  segment the first time it needs one.
- **Log layout** (`checkpoint.Config.Log`, in
  [checkpoint/log.go](../../checkpoint/log.go)). A checkpoint writes no page
  table. Its parts' tables already name its pages. It adds a log record to the
  table of its last part: its root without segments, its parent, the pages it
  zeroed and the map it replays from. That part's PUT is the commit. A VM's
  first checkpoint, a fork's first, and every `MapEvery` checkpoints also
  write a map object. A map object is an index object holding every segment.
  An open lists the VM's objects, reads the last map and every later part
  table at once, and replays the records along the parent chain. A log index
  holds its whole page table in memory, so no read fetches a segment.
  Reclamation can only delete what precedes the newest map, because every
  later record is replayed.

`TestLogLayoutMatchesIndexLayout` runs both layouts on one random history:
overwrites, zeroed pages, a shrink across a segment boundary, compaction, and
a fork under a pin. At every checkpoint both must read back the byte model and
locate every page at the same identity. Both must do so again after an open,
with the reopened root byte-identical to the published one.

## What was measured

`just compare-layouts` runs `TestCompareLayouts` at `cb80beb4` plus this
change. The VM has 2 GiB of RAM in 4 KiB pages and an 8 GiB root disk in 2 MiB
pages. Its first checkpoint writes half its RAM, scattered, and the first GiB
of its disk. A written page is an eighth random and the rest zero. The store
answers a GET or LIST in 10 ms and a PUT in 20 ms, at 500 MiB/s. Each layout
publishes through a host page cache. Opens and reads after them run on a
second store with an empty cache, as on another host. The log layout ran with
`MapEvery` 16 and 64.

The run found that the index layout fetched every segment it rewrote on every
checkpoint, one at a time: about 30 GETs and 300 ms each time. A new index did
not share the segments its parent had decoded. Both layouts now share them,
and the figures below include that fix.

The index layout uploads 1 to 1.7 MiB of index with every checkpoint, even one
of 64 pages. Scattered RAM writes touch all 32 segments of `ram0`, and a
touched segment is rewritten whole. A segment of 16,384 pages encodes to about
32 KiB. The log layout's records add nothing visible to the parts. Its map
objects cost about 2 MiB each, or 75 to 110 KiB a checkpoint at `MapEvery`
16.

A log checkpoint is one PUT round instead of two: its parts, then nothing. So
it commits in half the time, except when it also writes a map.

Compaction is identical in both layouts. The first runs of this comparison
found it reading each page it moved with its own serial GET: 12,932 GETs and
about 130 s a checkpoint at 32,768 pages, before either layout could commit.
TASK-29 made it read those pages in ranged extents, as a read does. The table
is after that change: 82 GETs and under 400 ms.

### Opening a checkpoint

An open on another host after each of 64 checkpoints of 1,024 RAM pages.

| layout | mean requests | worst requests | mean KiB read | mean ms | worst ms |
| --- | --- | --- | --- | --- | --- |
| index | 1.0 | 1 | 256.0 | 10 | 10 |
| log/16 | 10.4 | 35 | 2837.1 | 27 | 44 |
| log/64 | 49.9 | 87 | 9673.8 | 53 | 81 |

An index open is one GET of the root. A log open is a LIST, then the map and
every part table since it, read at once. Its cost grows with the records it
replays. The open is one or two round trips more, and it reads a whole map:
2 MiB for this VM.

### Reading after an open

One 4 KiB fault, then 64 read-ahead runs of 2 MiB of RAM at random, one after
another.

| layout | first fault requests | first fault ms | runs requests | runs ms | page entries at open | after runs |
| --- | --- | --- | --- | --- | --- | --- |
| index | 2 | 20 | 3050 | 4317 | 0 | 204669 |
| log/16 | 1 | 10 | 3026 | 4074 | 262524 | 262524 |
| log/64 | 1 | 10 | 3026 | 4074 | 262524 | 262524 |

The index layout's first fault also fetches a segment. So an open and a first
fault cost 30 ms in the index layout and 37 ms in log/16 on average. After
that, the index layout's runs are 6% slower, because each first touch of a
segment is one more request. The log layout holds its whole page table from
the start. The index layout holds 78% as much after 64 runs.

### What the store holds

Sampled after every checkpoint of the whole run and its reclamation.

| layout | checkpoints | mean part MiB | mean metadata MiB | mean total MiB | peak total MiB | final total MiB |
| --- | --- | --- | --- | --- | --- | --- |
| index | 206 | 461.57 | 54.38 | 515.95 | 672.54 | 646.69 |
| log/16 | 206 | 488.93 | 1.62 | 490.55 | 810.23 | 549.83 |
| log/64 | 206 | 567.47 | 1.26 | 568.74 | 810.38 | 549.83 |

The index layout's metadata averages a tenth of what it stores, and by the end
it is 149 MiB of 647. A segment stays in the index object of the checkpoint
that wrote it for as long as any root addresses it. So one live segment keeps
a whole object of up to 32 segments. The log layout stores almost no
metadata. It keeps dead parts longer, because only a new map frees anything:
log/64 holds 10% more than the index layout on average. Both log layouts peak
20% higher.

## What it means

The log layout is cheaper to publish. It takes one PUT and one round trip per
checkpoint instead of two, and almost no metadata bytes. At the current 60 s
interval that saves little: 3% of bytes, one PUT and 20 ms of each commit,
none of it on the pause path. It matters if the interval shrinks. At 1 s the
index layout nearly doubles what a checkpoint uploads.

It is dearer to open. An open is one or two round trips more, it reads a whole
map, and the host holds the whole page table in memory: about 24 bytes a page,
or 6 MiB for this VM in LSVD's own encoding. With `MapEvery` 16, an open plus
a first fault is 7 ms slower on average and 24 ms at worst.

It frees space later. What precedes the newest map is all it can delete, so
`MapEvery` trades open time against storage and map uploads. 16 is a
reasonable middle.

So the choice turns on the checkpoint interval. At 60 s the index layout is
fine. Below about 15 s its segment rewrites become a sixth or more of the
upload, and the log layout is worth its open cost.

## What this does not show

- The latency model is the simulator's. A real LIST is slower than a GET, and
  a VM with more than 1,000 objects needs more than one listing page.
- The workload is synthetic: uniform scattered RAM writes and one hot set.
  Real guests may touch fewer segments.
- The log layout is an experiment. It has no pull, no consistency check and no
  `Keep`. Its reclamation spares everything up to a pinned checkpoint.
