# Firecracker qualification on x86_64 GCE, 2026-09-27

The full qualification (`SPROUTFS_GCE_QUALIFY=1 scripts/bench-memory-gce.sh all`)
ran on GCE x86_64 in both arena modes, with every VMM of the Firecracker suite
jailed (`SPROUTFS_FIRECRACKER_JAIL=1`). This is the first recorded x86_64
qualification. The earlier ones were aarch64 only.

## Machine

- n2-standard-8 in us-east4-b: Intel Xeon (Cascade Lake, family 6 model 85) at
  2.80 GHz, 8 vCPUs.
- Ubuntu kernel 7.0.0-1011-gcp, x86_64.
- Nested KVM (VT-x with EPT) under the GCE hypervisor.

## Result

Every suite passed in both arenas except the Firecracker suite, where 67 tests
passed, 2 skipped and 4 failed. The skips are the guest workload benchmark,
which a qualification does not run, and `TestANestedVMIsRefusedOffX86`, which is
for the other architectures.

| suite | shared | isolated |
| --- | --- | --- |
| crate-clippy | pass | pass |
| crate-nextest | pass | pass |
| vmtest | pass | pass |
| vmmemory | pass | pass |
| pool-exhaustion | pass | pass |
| nested-kernel | pass | pass |
| firecracker-nested | pass | pass |
| firecracker | 4 failed | 4 failed |

The four failures had two causes, both in the jail rather than in the pager:

- A jailed VMM's directory was named for its VM, and with the long temporary
  directories the tests use, a socket path passed the 108 bytes a Unix socket's
  path may have. The directory is now named by its start number alone.
  `TestACheckpointDoesNotInterruptACommandRunningInTheGuest`,
  `TestAGuestTouchingAllItsRAMLeavesItsNeighbourItsWorkingSet` and
  `TestANestedGuestKeepsItsVMAcrossACaptureAndRestore` failed this way.
- `TestAFailedReleaseIsReportedOnce` started its fake VMM as root under a
  placement that names another user, which the new peer check refuses. The fake
  now drops to that user, as a jailed VMM runs.

The four tests, `TestJailedVMMsRunAsUsersOfTheirOwn` and
`TestAdversarialStarters` were then run again, jailed, in both arenas, and all
passed.

## Earlier runs the same day

Unjailed runs in both arenas found two failures that are fixed:

- the cold-copy give-back tests did not wait for the session's own pass;
- the dirty-budget test was sized for aarch64 guests, which touch fewer pages
  at boot than x86_64 guests do.
